# 图片存储方案与威胁模型

## 1. 目标与首版边界

NeighborMarket 的图片用于公开展示社区闲置物品，首版只支持每件物品一张主图。上传必须由后端认证、校验、解码和重新编码；浏览器不能指定服务器路径、对象键或任意外链 URL。本设计是 NM-E-05、NM-E-06 的实现依据，本批不新增接口、迁移、依赖或存储卷。

当前约束：

- `item.image_url` 是 `VARCHAR(500) NOT NULL`，发布服务目前写入外部占位图；演示数据使用 `/demo/...` 静态路径。
- 前端生产入口是非特权 Nginx，只有前端端口公开；后端和 MySQL 不映射宿主机端口。
- Compose 当前只有 MySQL 命名卷，应用容器重建不会保留本地上传文件。
- 物品编辑只允许发布者在 `AVAILABLE` 且无 `WAITING` 意向时执行，并使用 `expectedVersion` 与物品行锁防止条件被悄然改变。图片替换采用相同规则。

首版不包含多图、裁剪编辑、私密图片、客户端直传对象存储、内容审核、病毒扫描服务或 CDN。不得为展示技术而引入这些能力。

## 2. 架构决策

### 2.1 存储抽象

后端定义窄接口 `ImageStorage`，业务层只使用不可猜测的对象键，不依赖本地路径或某家云 SDK：

```text
store(validated stream, media type) -> StoredImage(key, size, mediaType)
delete(key)
open(key) / publicPath(key)
```

实现分两类：

| 环境 | 实现 | 持久化 | 公开读取 |
| --- | --- | --- | --- |
| 本地、演示、当前单机部署 | 文件系统适配器 | 独立命名卷挂载到后端，例如 `/var/lib/neighbormarket/images` | 同源 `/media/items/{key}` |
| 正式对象存储部署 | S3 兼容适配器 | 私有 Bucket | 同源代理或受控公开域名；数据库仍不接收用户 URL |
| 自动测试 | 临时目录适配器 | 每项测试独立临时目录 | MockMvc/服务层读取 |

本地卷不得放进前端镜像或源码目录。后端运行用户必须对挂载目录有读写权限，目录不能挂载为宿主机任意宽泛路径。对象存储凭据只能通过环境 Secret 注入，权限限制为指定 Bucket/前缀的读写删，不授予列出其他 Bucket 或管理权限。

### 2.2 数据库表示

首版继续使用 `item.image_url`，但业务上传值只能是后端生成的规范相对地址：

```text
/media/items/{两级分片}/{128-bit以上随机键}.{受控扩展名}
```

数据库不保存原始文件名、本地绝对路径、`file:` URI、用户提交的 URL、查询签名或对象存储密钥。`/demo/...` 仅为受信任演示数据兼容路径；新上传不得写入该前缀。长期若扩展多图、排序或审核状态，再以新 Flyway 迁移引入 `item_image` 表，不提前建模。

键使用加密安全随机值（UUID v4 的122位随机量或等价方案），按键前缀分片目录。扩展名由最终编码格式决定，不能沿用客户端文件名。每次替换生成新键，URL 永不覆盖，因此可使用不可变缓存并避免旧缓存展示新内容。

### 2.3 HTTP 契约

建议首版接口：

```text
PUT    /api/items/{id}/image     multipart/form-data
DELETE /api/items/{id}/image
GET    /media/items/{shard}/{key}.{ext}
```

写请求必须有 Session、CSRF Token 和 `expectedVersion`。只有发布者可写；只允许 `AVAILABLE` 且无 `WAITING` 意向的物品。替换或删除图片属于用户可见条件变化，必须与普通编辑采用相同的物品行锁顺序并令 `item.version + 1`。版本、状态或意向变化返回409；越权返回403；不存在返回404；格式或尺寸问题返回400；存储暂不可用返回503。响应和日志不能回显本地路径、对象凭据或解码器异常细节。

媒体读取是公开的，因为物品广场本身公开。响应必须包含准确的 `Content-Type`、`Content-Length`、`X-Content-Type-Options: nosniff`，且不允许内容协商成 HTML。上传后的唯一 URL可使用：

```text
Cache-Control: public, max-age=31536000, immutable
```

不存在的键返回404；路径不合法也统一返回404，不泄露目录结构。演示 `/demo/` 继续由前端静态资源提供，与 `/media/` 分离。

## 3. 文件接收与规范化

首版白名单仅为静态 JPEG 与 PNG：

| 项目 | 限制 |
| --- | --- |
| 单文件请求体 | 最大 8 MiB，在框架层和服务层双重限制 |
| 文件数量 | 每次恰好1个；每件物品最多1张当前主图 |
| 宽、高 | 各64～6000像素 |
| 总像素 | 最大20,000,000，防止解压炸弹 |
| 输入格式 | JPEG、PNG；必须由魔数和实际解码共同确认 |
| 明确拒绝 | SVG、GIF、WebP（首版无内置可靠解码器）、BMP、TIFF、ICO、PDF、HTML及任何可执行/压缩格式 |
| 原始文件名 | 只作非可信显示信息；不记录、不拼接路径、不用于类型判断 |

校验顺序必须限制资源消耗：

1. 在请求解析层限制总请求和文件字节数，超限立即停止读取。
2. 检查空文件；读取固定长度文件头并匹配 JPEG/PNG 魔数。
3. 选择明确的图片解码器，先读取宽高元数据；在分配完整像素缓冲区前检查单边和总像素限制。
4. 完整解码并拒绝损坏、截断、无法解码或包含异常帧的数据；设置处理超时和并发上限，避免 CPU/内存耗尽。
5. 重新编码为规范 JPEG 或 PNG，移除 EXIF、ICC 注释、GPS、缩略图及其他不需要的元数据。JPEG 自动纠正可信解析出的方向后再剥离 EXIF；PNG 动画或附加负载经静态重编码后不保留。
6. 对最终输出再次检查字节数和尺寸，使用随机键写入存储。服务端返回的类型取决于最终编码结果，而非请求头。

仅比较 `Content-Type`、扩展名或魔数都不够；三者不能替代完整解码与重新编码。SVG 即使声称是图片也必须拒绝，因为它可包含脚本、外部引用和复杂解析行为。

## 4. 一致性与生命周期

数据库事务和文件/对象存储不能形成单一 ACID 事务，替换流程采用补偿和可清理设计：

1. 在受限临时区接收、校验和重新编码；临时文件使用随机名、仅应用用户可读写，并设置短期清理。
2. 生成新不可变键并写入最终存储；写入必须使用“仅当键不存在”语义。本地实现先写同一文件系统临时文件，再原子移动。
3. 开启数据库事务，按既定顺序锁定物品行，检查发布者、`AVAILABLE`、`expectedVersion` 和无 `WAITING` 意向。
4. 条件更新 `image_url` 与 `version`，影响行数必须为1。数据库失败时立即尽力删除新对象；删除失败进入孤儿清理。
5. 数据库提交后再尽力删除旧的受管图片。旧值若是 `/demo/` 或占位图绝不删除。旧对象删除失败不能回滚已成功的用户操作，交给重试/清理任务。

服务崩溃可能留下未引用对象，因此需要可重复的只读扫描和显式清理模式：对超过24小时、且数据库不存在规范引用的受管对象标记为孤儿；至少再经过7天宽限才删除。清理必须限定受管前缀，支持 dry-run、数量上限和审计摘要，绝不能递归删除存储根或未知前缀。

物品进入 `RESERVED` 或 `COMPLETED` 后图片冻结并继续保留，用于交接和历史展示。当前没有删除物品功能，因此不定义级联删除；未来若增加删除，先软删除记录，再异步按保留期清理图片。备份必须同时覆盖 MySQL 与图片存储，并定期演练成对恢复；只备份数据库会产生永久断图。

## 5. 威胁模型

| 威胁 | 典型攻击/故障 | 控制措施 | 必测结果 |
| --- | --- | --- | --- |
| 路径穿越与覆盖 | 文件名为 `../../...`、绝对路径、重名覆盖 | 忽略原名；随机键；规范根目录校验；不存在式写入；本地原子移动 | 存储根外无写入，旧对象不变 |
| MIME 欺骗与主动内容 | `.jpg` 实为 HTML/SVG/脚本 | 字节上限、魔数、明确解码器、完整解码、重新编码、`nosniff` | 返回400且不产生对象/数据库引用 |
| 解压炸弹 | 小文件声明超大尺寸或高压缩像素 | 解码前宽高/像素检查、内存/并发/超时限制 | 稳定拒绝，不触发 OOM |
| 元数据隐私 | EXIF GPS、设备信息、嵌入缩略图 | 方向处理后重新编码并剥离元数据 | 下载结果不含原 EXIF/GPS |
| 越权修改 | 非发布者替换他人图片 | Session 身份、服务端发布者校验；不信任 publisherId | 403，文件与数据库均不变 |
| 旧页面覆盖 | 用户基于旧详情替换图片 | 必填 `expectedVersion`、物品行锁、条件 UPDATE | 409且新对象被补偿删除 |
| 条件偷换 | 有 WAITING 意向后替换图片 | 与编辑相同的状态/意向锁定检查 | 409且意向、版本、图片均不变 |
| CSRF | 第三方页面诱导上传/删除 | 现有 Cookie CSRF Token；SameSite；CORS 白名单 | 无 Token 的写请求为403 |
| 存储耗尽 | 大量上传、反复替换、并发编码 | 单文件/单物品限制、用户速率限制、全局容量告警、并发信号量、孤儿清理 | 429/413/503 可预测降级 |
| 对象枚举 | 顺序 ID 推测图片 | 128-bit以上随机键；不开放目录列表 | 无法按物品 ID 推导键 |
| 缓存错配 | 覆盖同 URL 后缓存仍是旧图 | 每次新键；不可变缓存；数据库原子切换引用 | 新响应使用新 URL |
| SSRF | 用户提交远程图片 URL 让后端抓取 | 首版只接收上传字节，拒绝 URL 导入 | 后端不发起用户控制的外连 |
| 解析器漏洞 | 恶意图片触发库漏洞 | 最小格式集、依赖锁定与扫描、处理隔离、及时升级 | 已知高危依赖阻断发布 |
| 备份不一致 | DB 恢复后对象缺失或反之 | 同批次快照、恢复演练、引用审计 | 恢复后引用完整率可核对 |

## 6. 配置与运维约束

建议配置项使用有界默认值并在生产启动时校验：

```text
APP_IMAGE_STORAGE_TYPE=filesystem|s3
APP_IMAGE_FILESYSTEM_ROOT=/var/lib/neighbormarket/images
APP_IMAGE_MAX_BYTES=8388608
APP_IMAGE_MAX_PIXELS=20000000
APP_IMAGE_MAX_DIMENSION=6000
APP_IMAGE_MIN_DIMENSION=64
APP_IMAGE_PROCESSING_CONCURRENCY=2
```

对象存储额外配置 Endpoint、Region、Bucket 和受管前缀，凭据沿用供应商标准 Secret 机制。日志只记录请求 ID、用户 ID、物品 ID、结果码、最终字节数/尺寸、耗时和不可逆的键摘要；不记录原图、完整对象键、原始文件名、EXIF 或凭据。指标至少包含上传成功/拒绝原因、处理耗时、输出大小、存储错误、补偿删除失败、孤儿数量和容量使用率。

Compose 实现 NM-E-05 时新增独立 `image-data` 命名卷，只挂载到后端的固定目录；不得复用 MySQL 卷。Nginx 可以把 `/media/` 代理到后端，首版不要求共享卷给前端容器。公网部署必须经 TLS，并在反向代理和 Spring 两层设置一致的请求体上限。

## 7. NM-E-05 实现与验收清单

实现顺序：

1. 增加 `ImageStorage`、文件系统实现、受限临时目录和配置校验；对象存储实现可后续按相同接口接入。
2. 增加图片验证/重编码服务，固定 JPEG/PNG 白名单及资源上限。
3. 增加带 `expectedVersion` 的替换/删除接口，复用物品编辑锁顺序、权限、状态和 WAITING 规则。
4. 增加同源媒体读取、Nginx `/media/` 转发、Compose `image-data` 卷和部署文档。
5. 增加补偿删除、孤儿审计 dry-run 和存储容量观测；清理删除可在证据充分后单独启用。

最低验收测试：

- 有效 JPEG/PNG 上传、读取、替换与删除；响应类型和 `nosniff` 正确。
- 空文件、超8 MiB、错误魔数、伪造 MIME、SVG/HTML、损坏图片、超尺寸和超像素全部拒绝。
- EXIF/GPS 被移除，原文件名无法影响对象键或目录。
- 未登录、缺 CSRF、非发布者、非 `AVAILABLE`、WAITING 意向和过期版本分别返回预期状态。
- 数据库更新失败会删除新对象；存储写入失败不改变 `image_url`/`version`；旧对象删除失败不破坏新引用并可被后续清理。
- 并发替换与编辑/申请只能有一个版本一致的赢家，不出现悬空引用或覆盖对象。
- 容器重建后图片仍存在；全新测试卷不会读取开发图片；备份/恢复说明覆盖数据库和图片卷。

只有上述安全、事务补偿和持久化测试通过后，NM-E-05 才能标记完成。前端预览、进度、失败重试和字段保留属于 NM-E-06。
