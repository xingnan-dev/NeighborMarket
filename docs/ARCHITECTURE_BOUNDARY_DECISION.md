# 架构边界复核记录

> 决策编号：NM-F-06  
> 日期：2026-10-19  
> 结论：保持 Vue SPA + Spring Boot 模块化单体 + 单 MySQL；当前不引入 Spring Cloud、微服务、Kafka 或 RabbitMQ。

## 1. 当前边界

生产拓扑由三个容器组成：Nginx 托管 Vue 静态资源并反向代理 API，单个 Spring Boot 后端处理认证和业务，单个 MySQL 保存权威数据。图片存放在独立持久卷，通过后端生成的不可变同源 URL 读取；AI 估价是可选的后端外部调用，失败时降级为手工填写价格。

后端按职责分包和分服务，但共同部署：

- `web` 负责 HTTP、认证主体和 DTO 边界；Controller 不直接访问 Mapper。
- `service` 内的物品、时段、意向、交接、留言和个人视图服务承载业务规则及事务。
- `mapper` 负责 MySQL 持久化、查询投影和原子条件更新。
- `dashboard` 负责只读聚合，仍以同一 MySQL 的真实记录为准。
- `image` 通过 `ImageStorage` 隔离存储实现和补偿清理。
- `ai` 通过 `PricingGateway` 隔离供应商协议，任何失败不阻断手工发布。

`ExchangeService` 只是兼容门面，不是远程服务边界。模块间调用是进程内 Java 调用，不伪装成网络 RPC。

## 2. 为什么保持模块化单体

物品编辑、领取申请、确认领取人、取消、完成和时段历史都依赖同一数据库内的行锁、条件 UPDATE、影响行数检查、外键/唯一约束和事务回滚。当前边界可以让状态变化与关联记录在一个本地事务内提交或全部回滚。

拆成独立服务后，需要决定数据所有权、跨服务认证、网络超时、重试幂等、分布式追踪和跨库一致性；关键流程还会从本地事务变成 Saga/补偿或最终一致性。当前没有独立团队、独立扩缩容、故障隔离或发布节奏证据可以抵消这些成本。

模块化单体已经提供当前需要的可维护性：Controller、Service、Mapper、外部适配器边界清楚，领域服务按职责拆分，并有架构、SQL 契约、事务和真实 MySQL 测试防止边界回退。

## 3. Spring Cloud 与服务发现

当前 Compose 只有一个后端实例，没有服务间调用，也没有动态服务发现、集中配置、网关路由或客户端负载均衡需求。Nginx 到后端只有固定单跳反向代理。

因此不引入 Spring Cloud Gateway、注册中心、配置中心或声明式服务客户端。若未来只有水平扩展同一后端，应先使用平台负载均衡、无状态化评估和 Session/限流决策，而不是把“多实例”直接等同于“微服务”。

## 4. Kafka/RabbitMQ 与异步边界

当前没有已确认的业务事件需要跨系统可靠投递：

- 发布、申请、确认、取消和完成都要求请求结束前返回权威状态，适合同步事务。
- 社区看板直接读取真实记录，不需要异步物化视图。
- AI 估价由用户主动请求并等待结果，且已有超时、限流和手工降级。
- 图片替换涉及数据库引用与文件补偿，当前本地流程已经定义提交前后清理顺序。
- 没有邮件、短信、推送、审计仓库、外部库存或数据管道消费者。

此时加入消息队列会新增 Broker、序列化版本、生产确认、消费幂等、重试/死信、顺序、积压监控和灾难恢复，却没有真实消费者。不能用“先发事件以后再用”作为采用理由。

## 5. 可接受的外部边界

当前保留两个可替换适配器，而不把它们拆成自建服务：

1. AI 供应商：由 `PricingGateway` 隔离，后端同步调用，失败可降级，不拥有核心业务状态。
2. 图片存储：由 `ImageStorage` 隔离，本地卷可在需求成立时替换为 S3 兼容对象存储；MySQL 只保存规范引用。

这两个边界证明模块化和端口适配器足以控制变化，无需为了外部依赖引入完整微服务平台。

## 6. 复评触发条件

满足具体需求后只复评相关边界：

1. 某模块需要独立扩缩容、独立发布或故障隔离，并有容量/可用性数据支持。
2. 出现独立团队和明确数据所有权，能够承担跨服务 API、兼容性和运维责任。
3. 出现必须可靠异步投递的真实消费者，例如通知、审计归档或外部系统集成，并明确至少一次投递下的幂等、顺序、重试和死信语义。
4. 单库成为经测量的容量或隔离瓶颈，且 SQL、索引、查询模型及纵向扩展已不足。
5. 已具备服务级监控、追踪、部署自动化、故障演练和数据迁移方案。

代码量增长、技术栈数量、未来可能扩容或“事件驱动更先进”不构成拆分条件。复评也不等于必然采用，必须比较保持单体的替代方案。

## 7. 最终决策

- NM-F-06：VERIFIED，继续保持模块化单体和单一权威 MySQL。
- 当前不采用 Spring Cloud、服务注册/发现、Kafka、RabbitMQ、分布式事务或事件溯源。
- Redis 继续遵循 NM-F-01 的条件决策；业务缓存继续遵循 NM-F-05 的场景化门槛。
- 下一步执行 NM-F-07，对 Phase F 的已完成决策、条件阻塞项和验证证据进行总验收。
