## 1. 可复现方式

基线由 `PerformanceBaselineIntegrationTest` 自动完成以下步骤：

1. 创建测试专用 MySQL 8.0 容器。
2. 从空库执行当前全部 Flyway V1～V8。
3. 在单个事务内生成固定规模的非生产数据。
4. 提交后执行 `ANALYZE TABLE`，避免批量装载后的统计信息失真。
5. 每条 SQL 先预热一次，再执行5次 `EXPLAIN ANALYZE`，记录客户端中位耗时和最后一次真实执行计划。
6. JVM 退出时由 Testcontainers 自动回收数据库。

执行命令：

```powershell
cd E:\NeighborMarket\backend
mvn "-Dtest=PerformanceBaselineIntegrationTest" test
```

该测试不读取项目 datasource 配置，不连接 `neighbor_market` 开发库，也不调用 AI 服务。Docker 不可用时会明确 skipped，不能视为基线通过。

## 4. 当前查询放大基线

以下数量根据 NM-C-01 采集时的 Service 调用链逐条计算，属于优化前基线；NM-C-02/NM-C-03 应用自动化查询计数补强证据：

| 业务调用 | 当前查询数量模型 | 代码原因 |
| --- | --- | --- |
| 市场列表 N 条 | `2 + N` | MyBatis-Plus 分页 count + page；`ItemService.view` 每件物品再查发布者 |
| 我的发布 N 条 | `3 + N` | 查当前用户 + 分页 count/page；每件物品再查发布者 |
| 物品意向 N 条 | `2 + 3N` | 查当前用户和物品；每条意向分别查用户、时段、物品 |
| 我的交接 H 条 | `2 + 3H` | 查当前用户和交接列表；每条交接分别查物品、发布者、领取人 |
| 我的看板 I 条意向、H 条交接 | `4 + 3I + 3H` | 两次当前用户查询、意向列表、交接列表，以及两个 DTO 转换中的逐行查询 |
| 物品留言 C 条 | `2 + C` | 校验物品、查留言列表；每条留言再查用户 |

这说明主要风险不只是单条 SQL 耗时：当前列表和“我的”页面存在随返回行数线性增长的数据库往返。优化时必须保持权限、排序、空关联和历史记录语义。

## 5. 基线揭示的问题与后续决策

1. 市场普通分页已有合适的 `(status, published_at, id)` 索引，本批次没有依据再添加重复索引。
2. `%keyword%` 在当前小数据和首页 LIMIT 下尚快，但前导通配符无法利用普通 B-Tree 定位文本。NM-C-05 应扩大数据规模或测试低命中/无命中词，再决定是否保留或评估 MySQL FULLTEXT；当前不引入 Elasticsearch。
3. `publisher_id = ? OR recipient_id = ?` 当前使用 index merge 后仍需排序。是否需要改写 UNION 或新增索引，应在 NM-C-04 用更大交接规模比较写放大与收益。
4. “最快完成”存在600次 item 主键回表，“最想要”是当前单条 SQL 基线中最重的查询。NM-C-04 应优先研究这两条计划，但不能为了毫秒级本地差异盲目增加索引。
5. N+1 的数据库往返预计比上述基础 SQL 本身更影响页面扩展性。NM-C-02 已完成物品列表治理；下一步应继续完成 NM-C-03 的查询计数与批量映射。

## 6. 后续对比规则

- 数据规模、字段分布、MySQL 版本、预热次数和采样次数保持不变。
- 同时报告客户端中位时间与 `EXPLAIN ANALYZE` 的实际行数/循环次数，不能只报告最快一次。
- N+1 优化必须报告业务调用总查询数，而不只展示某条 SQL 更快。
- 索引变更必须通过新 Flyway 迁移，并记录写入成本、磁盘成本和重复索引检查。
- 功能测试、并发测试和 V7 一致性审计必须继续通过。

## 7. NM-C-02 物品列表 N+1 优化结果

2026-10-09 在相同 MySQL 8.0、3,000件物品数据集上完成市场列表和“我的发布”优化。分页 SQL 现在在同一条语句的投影子查询中按发布者主键取得昵称，Service 不再对每条记录调用 `app_user.selectById`。

### 7.1 查询数量

查询数量由测试专用 MyBatis `StatementHandler.prepare` 拦截器统计实际预编译 SQL，而不是根据代码人工推测：

| 调用 | 优化前 | 优化后 | 验证规模 |
| --- | ---: | ---: | --- |
| 市场列表 | `2 + N` | `2` | 分别返回1条和12条，均为2条 SQL |
| 我的发布 | `3 + N` | `3` | 分别返回1条和10条，均为3条 SQL |

其中市场列表是分页 count + page；我的发布额外包含按 username 查询当前用户。测试同时验证发布者字段、关键词/分类筛选和 `published_at DESC, id DESC` 稳定排序。

### 7.2 执行计划对比

曾评估普通 `JOIN` 和 `STRAIGHT_JOIN`：MySQL 分别选择用户表驱动嵌套循环或哈希连接，均读取并排序全部1,800件 AVAILABLE 物品，客户端中位约8～9ms。该方案虽减少网络往返，却使单条列表 SQL 明显退化，因此未采用。

最终分页计划：

- `idx_item_market` 反向扫描，读取12行并立即满足 LIMIT 12。
- 投影子查询对 `app_user.PRIMARY` 执行12次单行查找，但全部发生在同一次数据库请求内。
- 市场首页客户端中位约1.397ms，对比 NM-C-01 原基础列表约1.557ms，没有观察到单条 SQL 回归。
- 关键词页为返回12行检查91件 AVAILABLE 物品，并执行12次发布者主键查找，中位约1.605ms。

因此本任务解决的是数据库往返 N+1，同时保留已有市场索引的 LIMIT 优势；没有新增索引或 Flyway 迁移。耗时差异处于本地测试噪声范围，可靠收益应以查询数从 `2 + N` 收敛到2为主。

## 8. NM-C-03 意向、交接与留言 N+1 优化结果

2026-10-09 将意向、交接、留言的读取路径改为专用联表投影。写入路径仍使用原领域实体与事务方法，避免性能改造改变并发状态机。实际查询数由与 NM-C-02 相同的 MyBatis 预编译语句计数器验证：

| 业务调用 | 优化前 | 优化后 | 固定组成 |
| --- | ---: | ---: | --- |
| 发布者查看物品意向 | `2 + 3N` | `3` | 当前用户、物品权限、联表意向列表 |
| 当前用户查看单个意向 | `2 + 3` | `2` | 当前用户、单条联表意向 |
| 我的交接 | `2 + 3H` | `2` | 当前用户、联表交接列表 |
| 交接详情 | `2 + 3` | `2` | 当前用户、单条联表交接及权限字段 |
| 物品留言 | `2 + C` | `2` | 物品存在性、联表留言列表 |
| 我的看板 | `4 + 3I + 3H` | `3` | 当前用户、联表意向列表、联表交接列表 |

集成测试在同一临时 MySQL 中放入多条结果并断言上述固定值，同时验证 DTO 字段、权限和稳定排序。历史意向仍能读取已设为 `active = false` 的交接时段；读取 JOIN 不按 active 过滤。V7 已通过外键保证用户、物品、时段及交接双方关联存在，所以使用 INNER JOIN 不会丢失合法记录，若关联缺失应作为数据完整性错误处理。

本任务没有增加索引：查询数量收敛已经得到直接证据，而索引是否调整留到 NM-C-04 使用既定3,000件物品数据集和 `EXPLAIN ANALYZE` 决策，避免把 N+1 修复与未经测量的写放大混在一起。

## 9. NM-C-04 关键查询与索引优化结果

2026-10-10 沿用3,000件物品、9,000条意向、1,200条交接的固定数据集，对生产 SQL 和候选 SQL 各预热1次并执行5次 `EXPLAIN ANALYZE`。下面数字来自同一轮 Docker/MySQL 环境，主要证据是执行计划和输入行数；毫秒值不作为生产 SLA。

| 查询 | 优化前中位 | 优化后中位 | 计划变化 | 决策 |
| --- | ---: | ---: | --- | --- |
| 我的交接联表 | 7.709ms | 2.952ms | 先关联用户会生成10,000行中间组合；`STRAIGHT_JOIN` 先用 publisher/recipient 索引合并筛为60行，再关联展示字段 | 采纳 |
| 最想要 Top 5 | 23.036ms | 16.443ms | item 主键查找从每条有效意向一次（9,000次）降为每个聚合 item 一次（3,000次） | 采纳 |
| 交接 `UNION ALL` | 7.417ms | 8.853ms | 仍出现用户表驱动和临时表排序 | 拒绝 |
| 最快完成改用 item 时间 | 3.546ms | 2.432ms | 可省去600次 item 主键关联，但完成时间来源由 handover 改为 item | 拒绝：历史语义无法保证等价 |

### 9.1 正确性验证

- 性能测试使用 JDBC 逐列比较“我的交接”和“最想要”优化前后的全部返回行及顺序，结果完全相同。
- “我的交接”仍按 `created_at DESC, id DESC` 排序，并继续由 Service 执行交接双方权限判断。
- “最想要”仍使用 `COUNT(DISTINCT user_id)`、只统计 WAITING/CONFIRMED，并排除 COMPLETED 物品；并列时仍按 `published_at ASC, id ASC` 稳定排序。
- 最快完成继续以 `handover.completed_at` 为权威字段，避免对缺少跨表时间一致性约束的历史数据改变排名。

### 9.2 索引结论

本轮没有新增索引或 Flyway 迁移。现有索引已经为采纳方案提供必要访问路径；继续添加 `(publisher_id, created_at)`、`(recipient_id, created_at)` 或新的意向覆盖索引，在当前数据规模下没有得到足以抵消存储和写放大的证据。NM-C-04 的结论是改写两条 SQL，并明确拒绝无依据索引，而不是为了形式增加迁移。

## 10. NM-C-05 搜索策略评估

2026-10-10 新增独立搜索测试库，从 Flyway V1～V7 空库迁移后生成30,000件 AVAILABLE 物品。数据包含高频中文关键词、390条完整英文 token 样本、1条唯一命中和无命中场景。每条 SQL 预热1次、执行5次 `EXPLAIN ANALYZE`；MyBatis-Plus 分页的列表和 count 分开测量。

| 场景 | 命中规模 | LIKE 列表中位 | LIKE count 中位 | 实际扫描特征 |
| --- | ---: | ---: | ---: | --- |
| 高频“普通” | 29,609 | 1.308ms | 32.135ms | 首页只检查14行即满足 LIMIT；count 扫描30,000行 |
| 低频 `baseline-target` | 390 | 2.609ms | 34.287ms | 首页检查801行；count 扫描30,000行 |
| 唯一 `unique-needle` | 1 | 39.228ms | 36.528ms | 列表和 count 都扫描30,000行 |
| 无命中 | 0 | 53.847ms | 36.130ms | 列表和 count 都扫描30,000行 |

`(status, published_at, id)` 仍有利于高命中首页按时间倒序提前满足 LIMIT，但普通 B-Tree 无法为前导 `%keyword%` 定位文本。分页 count 以及低命中/无命中列表的成本会随可搜索行数线性增长。

### 10.1 FULLTEXT 候选

测试库临时增加 `FULLTEXT(title, description)`，不写入生产迁移。对完整 token 的390条样本，FULLTEXT 列表中位3.623ms、count 2.634ms，并只读取390条全文索引结果。性能收益主要体现在 count 和低命中扫描。

但 FULLTEXT 不是兼容替换：`LIKE '%seline%'` 能命中全部390条包含 `baseline` 的记录，而 `MATCH ... AGAINST('seline')` 返回0。当前界面承诺“名称或描述”的任意子串搜索；直接切换还涉及中文分词、停用词、最小 token 长度、相关性排序和结果解释等产品语义变化。

### 10.2 当前决策与复评阈值

- 当前继续使用 LIKE，保留既有中文和词中片段语义；不新增生产索引或 Flyway 迁移。
- 当前不引入 Elasticsearch：30,000行最坏本机查询仍为数十毫秒，项目也没有相关性、多字段权重、拼写纠错或搜索集群需求。
- 当可搜索物品接近100,000级、搜索 p95 超过200ms、搜索导致数据库 CPU 明显升高，或产品接受“分词/前缀搜索”替代任意子串时，使用真实中文语料优先评估 MySQL ngram FULLTEXT。
- 只有 MySQL FULLTEXT 无法满足已经确认的相关性、语言分析、容错或独立扩缩容需求时，再评估专用搜索引擎。
