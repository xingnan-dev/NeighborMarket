## 2. 决策证据

### 2.1 Redis、Session 与共享限流

- `compose.yml` 只有一个 Spring Boot 后端实例，没有负载均衡或水平扩展配置。
- Spring Security 使用进程内 HttpSession；当前不存在跨实例登录态漂移。
- AI 冷却按用户名在单进程内原子执行。没有真实生产 AI 调用量、跨重启严格预算或跨实例配额需求。
- 引入 Redis 会新增连接、超时、认证、容量、淘汰、监控、备份和故障降级责任，当前收益不足。

因此 NM-F-03 和 NM-F-04 保持条件阻塞。若前置条件未来成立，应重新执行决策和集成测试，而不是直接把当前状态改为 VERIFIED。

### 2.2 AI 可观测性与隐私

`AiPricingTelemetry` 提供：

- `neighbormarket.ai.pricing.requests` Counter；
- `neighbormarket.ai.pricing.duration` Timer；
- `estimate`、信息不足、本地/供应商限流、超时、未配置、供应商错误、无效响应等固定结果类别；
- 每进程随机盐生成的匿名用户键，只用于结构化日志且不作为指标标签。

日志和指标禁止包含用户名、物品名称/描述、Prompt、供应商请求/响应、密钥和异常正文。Actuator 仍只公开 `health,info`。供应商未返回统一可信 usage 时，不虚构 token 或人民币成本。

### 2.3 缓存决策

- 普通读取已经消除主要 N+1，固定数据集下保持毫秒级，没有生产数据库压力证据。
- 市场搜索的关键词、筛选、分页组合键基数高；任一物品写入可能影响多个列表、count 和页边界。
- 缓存不能解决 `LIKE '%keyword%'` 的首次线性扫描。达到既定容量和 p95 阈值后，应先评估 MySQL ngram FULLTEXT。
- 用户权限、物品版本、意向和交接状态不缓存，避免陈旧数据误导操作。
- 图片使用替换即新键的不可变 URL，因此继续使用一年 `public, immutable` HTTP 缓存。

### 2.4 架构边界

核心状态转换依赖同一 MySQL 事务内的行锁、条件 UPDATE、影响行数检查、外键/唯一约束和失败回滚。当前没有独立团队、独立扩缩容、独立发布、故障隔离或可靠异步消费者需求。

因此继续使用模块化单体；不采用 Spring Cloud、服务注册发现、Kafka、RabbitMQ、分布式事务或事件溯源。AI 与图片存储通过 `PricingGateway` 和 `ImageStorage` 适配器隔离变化，无需拆成自建服务。

## 4. 残余风险与复评门槛

| 风险/未知项 | 当前处理 | 复评触发条件 |
| --- | --- | --- |
| 单实例 AI 限流在重启后重置 | 接受当前近似冷却；手工发布始终可用 | 多实例、跨重启严格预算或真实成本风险成立 |
