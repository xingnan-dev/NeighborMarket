# 技术选型与取舍

本文对应 NM-G-09，集中说明 NeighborMarket 当前采用的技术、被否决的替代方案、决策证据和复评条件。选择目标是保障社区闲置流转中的安全、数据正确性和可重复交付，不以组件数量作为完成度。

## 1. 决策摘要

| 领域 | 当前选择 | 主要原因 | 何时复评 |
| --- | --- | --- | --- |
| 应用形态 | Vue SPA + Spring Boot 模块化单体 | 业务规模与团队边界集中；核心流程需要同库事务 | 出现独立团队、独立扩缩容或故障隔离需求 |
| 权威数据 | MySQL 8 + Flyway | 关系、约束、事务和行锁适合物品/意向/交接模型 | 单库经优化后仍成为已测量瓶颈 |
| 并发控制 | 行锁、条件 UPDATE、版本号、数据库约束 | 不依赖先读结果；失败可返回稳定 409 | 冲突率、事务时长或分库需求发生实质变化 |
| 数据访问 | MyBatis-Plus + 显式 SQL | 常规 CRUD 简洁，关键 SQL/更新条件可见且可测 | 查询模型复杂到需要新的明确抽象时 |
| Session | Spring Security HttpSession | 当前单后端实例，安全机制成熟且成本低 | 多实例且不能采用可靠粘性会话 |
| 缓存 | 不缓存业务数据；图片使用不可变 HTTP 缓存 | 缺少热点证据，业务状态失效面大 | 指标证明重复热点造成数据库压力 |
| Redis | 当前不引入 | 无跨实例 Session、严格共享限流或安全缓存需求 | 多实例或严格跨实例配额成为真实需求 |
| MQ/微服务 | 当前不引入 | 没有独立消费者或数据所有权边界 | 出现可靠异步消费者或独立服务边界 |
| AI | 后端 OpenAI-compatible 适配器，可选且可降级 | 密钥留在服务端，供应商可替换，失败不阻断发布 | 成本、质量或供应商约束要求更换方案 |
| 部署 | Docker Compose：Nginx、应用、MySQL | 当前规模可重复部署，组件和恢复边界清楚 | 可用性目标要求编排平台或多实例 |

## 2. 为什么选择模块化单体

发布、编辑、申请、确认、取消和完成会同时改变物品、时段、意向与交接。当前实现可以在一个 Spring/MySQL 本地事务中完成这些写入，任一步失败都整体回滚。模块按 Web/Security、物品、交换工作流、看板、图片和 AI 分离，但仍以进程内调用协作。

拆成微服务会立即引入跨服务身份、网络失败、重试幂等、数据所有权、分布式追踪和 Saga/补偿，却没有独立团队、独立发布或独立扩缩容收益。代码量增加或“未来可能扩容”不是拆分依据。完整边界见 [架构边界复核](ARCHITECTURE_BOUNDARY_DECISION.md)。

## 3. 为什么选择 MySQL 和 Flyway

核心模型具有明确关系：用户发布物品，物品包含时段和意向，并最多关联一个活动交接。MySQL 提供当前需要的能力：

- 本地 ACID 事务保证关联状态一起提交或回滚。
- `SELECT ... FOR UPDATE` 和条件 UPDATE 提供竞争顺序与胜负判定。
- 外键、唯一键、CHECK、生成列唯一索引防止非法关联和多条活动交接。
- 常规 B-Tree、聚合和 `EXPLAIN ANALYZE` 足以支持当前数据量与查询证据。
- Flyway V1～V8 只追加迁移，使空库初始化与已有数据升级采用同一路径。

当前不采用 NoSQL：主要数据不是无约束文档，关键需求反而依赖跨表关系和事务。当前也不引入 Elasticsearch；任意子串搜索在既定基线内尚可接受，达到容量和延迟阈值后先评估 MySQL ngram FULLTEXT，详见 [SQL 性能报告](PERFORMANCE_BASELINE.md)。

## 4. 为什么并发控制不是单一机制

不同竞争使用不同但互补的数据库机制：

- **行锁**：编辑与申请先锁同一物品行，以固定顺序串行业务条件检查。
- **版本号**：客户端携带 `expectedVersion`；过期页面不能覆盖较新的编辑或状态。
- **条件 UPDATE**：确认只允许 `AVAILABLE -> RESERVED`，取消/完成只允许从 `ACTIVE` 转换；影响行数必须为 1。
- **数据库约束**：即使应用逻辑回退，唯一键、复合外键和 CHECK 仍拒绝非法最终状态。
- **事务回滚**：条件失效或中途异常时，不保留部分字段、交接、时段或指针更新。

只使用乐观锁无法表达“每件物品最多一个活动交接”；只使用悲观锁无法防止遗漏锁或未来代码回退；只靠前端按钮禁用更不能保证多会话正确性。组合方案让业务胜负、过期写入和最终数据形态各有对应防线。详见 [状态机与并发时序](STATE_MACHINE_AND_CONCURRENCY.md)。

## 5. 为什么选择 Session，而不是 JWT

当前是同源浏览器应用和单后端实例。Spring Security Session 配合 HttpOnly/SameSite Cookie、生产 Secure Cookie、CSRF token、登录时 Session ID 轮换和服务端注销，能够直接满足认证需求。

JWT 不会自动解决撤销、浏览器安全或多实例问题；若放在可被脚本读取的位置还会扩大 XSS 后果，若仍放 Cookie 中则同样需要 CSRF 防护。当前没有第三方客户端、跨域 API 网关或无状态多实例的明确需求，因此不增加 token 刷新、撤销列表和密钥轮换复杂度。

若未来扩展多实例，应先明确负载均衡和登录态目标；无法使用可靠粘性会话时，再评估 Spring Session Redis，而不是默认改用 JWT。

## 6. 为什么暂不引入 Redis 和业务缓存

当前只有一个应用实例；Session 不需跨实例共享，AI 60 秒冷却不需全局分布式计数。性能基线表明主要 N+1 已消除，普通读取为固定查询数，尚无生产热点、命中率或数据库饱和证据。

物品、搜索、看板和用户状态会被发布、编辑、申请、确认、取消与完成频繁影响。缓存会增加键设计、精确失效、允许陈旧时间、容量、淘汰、监控和故障回源责任，却未证明收益。图片是例外：替换会生成新 URL，因此可以安全使用一年不可变 HTTP 缓存。

采用 Redis 前必须有明确用途和指标，而不是先部署再找场景。详细门槛见 [Redis 决策](REDIS_DECISION.md) 与 [缓存决策](CACHE_DECISION.md)。

## 7. 为什么暂不引入消息队列

核心写操作需要请求结束前返回权威状态，适合同步事务。当前没有邮件、短信、推送、审计仓库、外部库存或数据管道等可靠异步消费者。AI 是用户主动等待的可降级调用；看板直接查询权威记录；图片引用切换已有事务与补偿边界。

没有消费者时加入 Kafka/RabbitMQ，只会新增消息版本、生产确认、至少一次投递下的消费幂等、顺序、重试、死信、积压监控和 Broker 灾难恢复。只有出现真实消费者，并明确允许的延迟、重复和失败语义后才复评。

## 8. 外部能力为什么使用适配器

AI 通过 `PricingGateway` 隔离 OpenAI-compatible 协议，图片通过 `ImageStorage` 隔离本地卷实现。两者都不拥有核心交换状态：

- AI 密钥和 Prompt 留在后端，输出经过结构校验；未配置、限流、超时或供应商失败时回到手工定价。
- 图片先写新对象，再在数据库中切换规范引用，失败执行补偿；未来可在需求成立时替换为对象存储。

这种端口适配器边界已经控制供应商变化，无需把外部依赖包装成自建微服务。

## 9. 复评方法

任何技术复评都应记录当前指标、目标、候选方案、故障语义、迁移与回滚方案，再做最小验证。以下情况只触发复评，不代表自动采用：

1. 后端扩展到两个或更多实例，需要共享 Session 或严格跨实例 AI 配额。
2. 某模块存在独立团队、发布节奏、扩缩容或故障隔离要求。
3. 出现必须可靠异步投递的真实消费者。
4. MySQL 在 SQL、索引、查询模型和容量优化后仍成为已测量瓶颈。
5. 生产请求证明某类可安全失效的读取具有稳定高重复率。
6. 搜索规模、p95 或数据库 CPU 达到性能报告中的复评阈值。
7. 可用性目标超过单机 Compose 能力，并已具备监控、备份恢复和故障演练基础。

最终原则：先用最少组件保证正确性和可运维性；只有证据表明现有边界不足时，才承担新组件的运行与一致性成本。
